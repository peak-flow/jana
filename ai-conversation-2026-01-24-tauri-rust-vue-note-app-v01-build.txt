⏺ Good choices. Let me address each point honestly:

  Alpine.js vs Vue: Alpine is great for sprinkling interactivity on
  server-rendered pages, but for a desktop app with a code editor (CodeMirror
  6), state management (notes list, editor content, AI panel), and component
  structure — Vue is genuinely better suited. CodeMirror 6 integrates cleanly
  with Vue via reactive bindings. Alpine would fight you here. I'd recommend Vue
   3 (Composition API, lightweight).

  Go backend — here's the issue: Tauri's backend is Rust. That's not optional —
  it's how Tauri works. You can't swap it for Go. You have two real options:

  1. Tauri (Rust backend) + Vue frontend — The Rust is minimal (just Tauri
  commands that bridge to SQLite). Most logic lives in the frontend. You'd
  barely write Rust beyond boilerplate.
  2. Go backend + webview — Use something like https://wails.io instead of
  Tauri. Wails is essentially "Tauri but with Go." Same concept: native webview,
   Go backend, web frontend. This gives you Go for the backend exactly as you
  want.

  Given you want Go specifically for speed and simplicity, Wails is the right
  call over Tauri.

  Autosave: I'd suggest a 2-second debounce after last keystroke + save on 
  blur/window unfocus. This avoids hammering SQLite on every character but
  ensures nothing is lost. Simple and reliable.

  Revised stack:
  - Wails (Go backend, native webview)
  - Vue 3 (frontend, Composition API)
  - CodeMirror 6 (editor)
  - SQLite (via Go — modernc.org/sqlite or mattn/go-sqlite3)
  - Local LM Studio (qwen3-vl-30b at 192.168.77.1:1234)
  - Minimal sidebar + editor + summary panel

  Does this stack work for you, or do you have concerns about any of these
  choices?

❯ What about using tauri plus sidecar go binary? Would that work? 

⏺ Yes, that works. Tauri supports sidecars natively — you bundle a Go binary
  alongside the app, and Tauri spawns/manages it as a child process. The
  frontend communicates with the Go sidecar via HTTP (localhost) or
  stdin/stdout.

  How it would work:

  ┌─────────────────────────────────┐
  │  Tauri Shell (Rust - minimal)   │
  │  - Spawns Go sidecar on launch  │
  │  - Window management            │
  ├─────────────────────────────────┤
  │  Vue 3 + CodeMirror 6 (webview) │
  │  - UI, editor, sidebar          │
  │  - Calls Go sidecar via HTTP    │
  ├─────────────────────────────────┤
  │  Go Sidecar (separate binary)   │
  │  - SQLite CRUD                  │
  │  - LLM calls to LM Studio      │
  │  - Runs on localhost:PORT       │
  └─────────────────────────────────┘

  Pros:
  - You write all backend logic in Go
  - Tauri handles window/native OS stuff (tray, menus, packaging)
  - Clean separation: Go does data/AI, frontend does UI
  - Tauri's sidecar management handles lifecycle (start/stop with app)

  Cons:
  - Two binaries to build/bundle (Tauri handles this, but adds build complexity)
  - Inter-process communication overhead (negligible for this use case — local
  HTTP on loopback is ~0.1ms)
  - Slightly larger app size vs pure Wails

  vs Wails:
  - Wails is simpler (one binary, Go bindings directly callable from JS)
  - Tauri + sidecar gives you Tauri's ecosystem (plugins, updater, etc.) but
  more moving parts

  For a v0.1 note app, the sidecar approach is honestly over-engineered compared
   to Wails. But if you want Tauri's packaging/update system or plan to use
  Tauri plugins later, it's a valid path.

  My recommendation: Wails for simplicity now, unless you have a specific reason
   to want Tauri's features.

❯ if i give someone else "src-tauri/target/release/bundle/macos/CC          
  Sublime.app" can they run app or do they need to build on their systme?   

⏺ They can run it directly — no build tools needed. The .app bundle contains the
   compiled Rust binary + all frontend assets. It uses the system WebKit webview
   (already on every Mac).

  Caveats:

  1. Architecture: You built for aarch64 (Apple Silicon). It only runs on other
  Apple Silicon Macs. For Intel Macs you'd need to cross-compile with cargo 
  tauri build --target x86_64-apple-darwin.
  2. Gatekeeper warning: Since the app isn't code-signed, recipients will see
  "app can't be opened because it is from an unidentified developer." They can
  bypass via right-click → Open, or System Settings → Security.
  3. LLM feature: The Summarize button calls 192.168.77.1:1234 — that's your
  local network. It won't work on someone else's machine unless they have their
  own LM Studio running at the same address (or you change the endpoint).
  4. DMG is easier to share: Send the .dmg file instead — it's a proper
  installer image:
  src-tauri/target/release/bundle/dmg/CC Sublime_0.1.0_aarch64.dmg

❯ What about using tauri plus sidecar go binary? Would that work? 

⏺ Yes, that works. Tauri supports sidecars natively — you bundle a Go binary
  alongside the app, and Tauri spawns/manages it as a child process. The
  frontend communicates with the Go sidecar via HTTP (localhost) or
  stdin/stdout.

  How it would work:

  ┌─────────────────────────────────┐
  │  Tauri Shell (Rust - minimal)   │
  │  - Spawns Go sidecar on launch  │
  │  - Window management            │
  ├─────────────────────────────────┤
  │  Vue 3 + CodeMirror 6 (webview) │
  │  - UI, editor, sidebar          │
  │  - Calls Go sidecar via HTTP    │
  ├─────────────────────────────────┤
  │  Go Sidecar (separate binary)   │
  │  - SQLite CRUD                  │
  │  - LLM calls to LM Studio      │
  │  - Runs on localhost:PORT       │
  └─────────────────────────────────┘

  Pros:
  - You write all backend logic in Go
  - Tauri handles window/native OS stuff (tray, menus, packaging)
  - Clean separation: Go does data/AI, frontend does UI
  - Tauri's sidecar management handles lifecycle (start/stop with app)

  Cons:
  - Two binaries to build/bundle (Tauri handles this, but adds build complexity)
  - Inter-process communication overhead (negligible for this use case — local
  HTTP on loopback is ~0.1ms)
  - Slightly larger app size vs pure Wails

  vs Wails:
  - Wails is simpler (one binary, Go bindings directly callable from JS)
  - Tauri + sidecar gives you Tauri's ecosystem (plugins, updater, etc.) but
  more moving parts

  For a v0.1 note app, the sidecar approach is honestly over-engineered compared
   to Wails. But if you want Tauri's packaging/update system or plan to use
  Tauri plugins later, it's a valid path.

  My recommendation: Wails for simplicity now, unless you have a specific reason
   to want Tauri's features.

  Caveats:

  1. Architecture: You built for aarch64 (Apple Silicon). It only runs on other
  Apple Silicon Macs. For Intel Macs you'd need to cross-compile with cargo 
  tauri build --target x86_64-apple-darwin.
  2. Gatekeeper warning: Since the app isn't code-signed, recipients will see
  "app can't be opened because it is from an unidentified developer." They can
  bypass via right-click → Open, or System Settings → Security.

  local network. It won't work on someone else's machine unless they have their
  own LM Studio running at the same address (or you change the endpoint).
  4. DMG is easier to share: Send the .dmg file instead — it's a proper
  installer image:
